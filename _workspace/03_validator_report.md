## 4. WARN (13건)

### 4-1. 발성 도서 1종 — 13일 (10-16, 그리고 10-19 ~ 11-06 의 12일)

- **원인:** 10-16 에 레바논 녹음이 끝나면 잔여 녹음 도서가 사도행전 1종뿐이다. 혼합할 상대가 물리적으로 존재하지 않는다.
- **판정: 구조적으로 불가피.** 재배분으로 해소 불가 — 다른 도서를 뒤로 미루려면 성경(10-15 편집 마감)·레바논(11-06 편집 마감) 둘 다 마감을 넘긴다. `min_books_per_recording_day` 를 2→1 로 낮춘 제약 파일의 판단은 타당하다.
- **완화 적용 여부: 부분 적용.** 12일(10-19~11-06)은 레바논 편집 블록이 동반되어 *작업 종류*는 2종이고 일부하 10p(상한의 25%)로 낮다. 10-16 은 17p 단독.
- **단, 이전 세대에서 적용했던 세션 분할이 이번에는 빠졌다.** 이전 계획은 단일 도서 5일(36~38p)에 오전/오후 분할을 적용했다. 이번 12일은 10p 라 발성 부하 관점의 분할은 불필요하다는 옵티마이저 판단에 동의한다 — 10p 세션을 둘로 쪼개는 것은 실익이 없다. **다만 단조로움은 부하가 아니라 기간의 문제이고, 여기서는 3주 연속이다.** 결론은 4-3 참조.

## 5. 스크립트 미포괄 정성 평가

### 5-1. 전일 점유일의 요일 선택 — **문제 있음 (성대 회복 논리 역행)**

유튜브 전일 녹음은 **페이지 예산만 비소비일 뿐 발성 작업**이다. 휴식일이 아니다.
월→화 변경의 실제 효과를 전날 부하로 보면:

```
유튜브 2026-09-29(화) 전날 2026-09-28: 35p recording   ← 35p 다음날 전일 발성
유튜브 2026-10-06(화) 전날 2026-10-05: 무배치(제외일)
유튜브 2026-10-13(화) 전날 2026-10-12: 35p recording   ← 35p 다음날 전일 발성
유튜브 2026-10-20(화) 전날 2026-10-19: 10p recording
유튜브 2026-10-27(화) 전날 2026-10-26: 10p recording
유튜브 2026-11-03(화) 전날 2026-11-02: 10p recording
```

- 구 계획(월요일)에서는 전일 녹음이 **주말 휴식 직후**에 놓였다. 화요일로 옮기면서 9-29 와 10-13 두 번은 **최대 부하 35p 월요일 바로 다음날**에 전일 발성이 온다. 이것이 계획 전체에서 가장 무거운 2일 연속 구간이다.
- 최장 연속 근무 구간도 여기다: `9-28(35p) → 9-29(전일) → 9-30(35p) → 10-01(35p) → 10-02(35p)` — **5일 연속 발성, 휴식일 0.**
- **판정: 불가피하지 않다. 그러나 사용자 지시 사항이다.** 제약 파일 `notes` 에 "요일 변경: 월요일 → 화요일 (사용자 지시)" 로 명시되어 있으므로 옵티마이저의 재량 위반이 아니고, 스케줄 FAIL 도 아니다. **사용자에게 트레이드오프를 고지할 사항**으로 올린다 — 화요일 고정을 유지하려면 9-28·10-12 월요일 부하를 35p → 20p(레바논만)로 낮추고 성경 15p 를 뒤로 미루는 선택지가 있으나, 성경은 버퍼 0일이라(5-3) 그 여유가 없다. 즉 **현 제약 조합에서는 완화 수단이 없다.**

### 5-2. 편집일 배치 — **적합**

- 성경 전일 편집 10-15(목)는 `10-12(35p) → 10-13(전일 유튜브) → 10-14(32p)` 3일 연속 발성 직후에 놓였다. 계획 내 유일한 **완전 무발성 휴식일**로 이중 기능하며 배치 위치가 정확하다.
- 레바논 편집 12일은 녹음 부하가 10p 로 떨어진 이후 구간과 겹쳐 발성 총량이 낮다.

### 5-3. 주별 부하 분산 — **평탄하지 않다 (다만 재량 없음)**

```
주별 페이지  W1 35 / W2 140 / W3 70 / W4 84 / W5 40 / W6 40 / W7 40
녹음일 부하  35 ×8, 32 ×1, 17 ×1, 10 ×12     (평균 20.4p)
```

- 이중 봉우리 분포다. 앞 9일은 상한의 87.5%(35p), 뒤 12일은 25%(10p). 평균 20.4p 는 밴드 `[10,35]` 안이지만 **어떤 날도 평균 근처에 없다.**
- **판정: 재배분 불가.** 사용자가 도서별 일일 속도(성경 15p / 레바논 20p / 사도행전 10p)를 직접 지정했으므로 평준화 재량이 없다. 스케줄 `meta.strategy` 의 "최적화 결과가 아니라 지정 속도의 전개"라는 서술이 정확하다.
- 다만 뒤 12일에 **일 30p × 12일 = 360p 의 유휴 용량**이 있다는 사실은 5-5 의 사도행전 분량 리스크를 흡수할 여력으로 남는다.

### 5-4. 버퍼 0일 리스크 — **위험도 높음. 단 위험은 p4 가 아니라 p1 에 집중된다**

제약·스케줄 양쪽 `risk_notes` 는 "하루 빠지면 사도행전이 120p→110p 로 바뀐다"고 적었다. **이 서술은 위험의 방향을 잘못 짚었다.**

```
p1(9/23~10/14) 평일 16 − 제외 4 − 유튜브 3 = 가용 9일 / 성경 필요 9일 → 여유 0일
```

- 사도행전 총량은 일정에서 **역산된 값**이다. 따라서 p4 에서 하루가 빠져도 "120p 를 못 채움"이 아니라 "애초 목표가 110p 였던 것"이 된다 — 정의상 깨질 수 없다. p4 는 사실상 완충 구간이다.
- **진짜 파단면은 p1 이다.** 9-23 ~ 10-14 구간의 가용일은 정확히 9일이고 성경은 정확히 9일을 요구한다. 이 구간에서 하루라도 빠지면 성경 9일차가 10-15 로 밀리고, 전일 편집이 10-16 으로, 레바논 잔여 17p 가 10-19 로 밀린다. **성경 마감 10-15 가 즉시 깨진다 (하드 FAIL).**
- 동일하게 레바논 녹음 완료 10-16 도 여유가 없다.
- **회복 레버 (현재 계획 변경 아님, 유사시 대응안):** 성경 일일 속도를 15p → 17p 로 올리면 132p 를 8일에 소화한다(17×7 + 13). 그 날 부하는 17 + 20 = **37p 로 상한 40p 이내**다. 즉 **상한을 깨지 않고 p1 에 버퍼 1일을 만들 수 있는 여지가 존재한다.** 하루를 잃었을 때 재배분을 요청하지 않고도 복구 가능하다는 뜻이므로, 이 사실을 계획 산출물에 남겨둘 것을 권한다.

### 5-5. 사도행전 120p 가 역산값인 점의 파급 — **UI/실적 추적이 먼저 깨진다**

실제 분량이 120p 가 아닐 때 무엇이 깨지는지를 단계별로:

1. **하드 제약은 깨지지 않는다.** 스케줄 내부는 자기일관적이다(12일 × 10p).
2. **실제 > 120p 인 경우:** 11-06 안에 못 끝낸다. 대응은 (a) 종료일 연장 또는 (b) 일일 속도 상향. **(b)가 사실상 무비용이다** — p4 일부하가 10p 로 상한 대비 30p 여유가 있어, 속도를 20p/일로 올리면 240p 까지 같은 12일 안에 흡수된다. 발성 부하 관점에서 이 리스크는 **낮다.**
3. **실제 < 120p 인 경우:** 조기 종료. 문제 없음.
4. **실제로 깨지는 것은 진도 추적이다.** `index.html` 의 진행률·쿠폰 임계값은 총 449p 와 도서별 계획값을 분모로 쓴다. 사도행전 분모 120p 가 허수이면 **사용자가 보는 진행률이 틀린다.** 실적은 `localStorage`(`voxplan.checkins.v1`)에만 있어 레포에서 읽을 수 없으므로 자동 보정도 불가능하다.
5. **권고:** UI 발행 단계(Phase 5)에서 사도행전 블록에 "총량 미확정(일정 역산값)" 표시를 달거나, 사용자에게 실제 페이지 수를 먼저 확인할 것. 이 값은 나머지 두 도서처럼 사용자가 준 값이 아니다.

### 5-6. 단일 도서 13일의 단조로움 — **세션 분할 불필요, 대신 표기 분리 권고**

- 발성 부하 기준으로 10p 는 상한의 25%다. 이 분량을 오전/오후로 쪼개는 것은 이전 세대(36~38p 단일 도서 5일)와 달리 실익이 없다. **세션 분할은 적용하지 않는 것이 옳다.**
- 단조로움의 실체는 부하가 아니라 **3주 연속 같은 도서**라는 기간이다. 완화 요인은 같은 날 레바논 편집이 붙어 작업 종류가 2종이라는 점이다.
- **결론: 추가 완화 불필요.** 단, UI 에서 해당 날이 "사도행전 10p" 한 줄로만 보이면 실제로 하는 일(편집 + 녹음)이 드러나지 않는다. **편집 블록과 녹음 블록을 시각적으로 구분해 렌더링할 것** — 이것이 이 구간에 실제로 필요한 유일한 완화다.
