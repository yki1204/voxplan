# 녹음 제약 모델링

배분을 짜기 전에, 요건을 숫자로 바꾸고 **그 배분이 애초에 존재할 수 있는지** 판정한다.

## 왜 타당성을 먼저 계산하는가

배분안을 다 만든 뒤 "총 페이지가 상한 용량을 넘었다"를 발견하면, 배분 전체를 버려야 한다. 반대로 타당성 판정은 나눗셈 몇 번이면 끝난다. 그리고 불가능한 경우 사용자가 알아야 하는 것은 예쁜 일정표가 아니라 **얼마나 초과했고 무엇을 양보해야 하는지**다.

## 1단계: 기간 해석

기간 표현은 대개 중의적이다. 특히 "한달 반", "두 달", "분기" 는 근무주 기준과 캘린더 기준이 다르다.

| 표현 | 근무주 해석 | 캘린더 해석 |
|------|------------|------------|
| 2주 | 평일 10일 | 시작+14일 |
| 1달 | 평일 20일 | 시작+1개월 |
| 한달 반 | 평일 30일 (6주) | 시작+45일 (≈7주) |

**두 해석을 모두 계산하고 결과를 나란히 보여준다.** 한쪽만 골라 진행하면, 불가능한 해석을 고른 경우 사용자는 "왜 안 되는지" 대신 "왜 이상한 일정인지"를 받게 된다.

날짜와 요일은 절대 암산하지 않는다. 코드로 확인한다:

```python
import datetime as dt
def weekdays(start, end):
    d, e, out = dt.date.fromisoformat(start), dt.date.fromisoformat(end), []
    while d <= e:
        if d.weekday() < 5: out.append(d)
        d += dt.timedelta(days=1)
    return out
```

## 2단계: 가용 녹음일 계산

이 도메인에서 가장 흔한 오류는 **전일 점유일을 빼지 않는 것**이다.

```
가용 녹음일 = 전체 근무일
            − 주간 전일 녹음일 (주 1일 × 주 수)
            − 편집 전일 (도서별 edit_full_days 합)
```

전일 점유일은 페이지 예산을 전혀 소비하지 않으면서 날짜를 잡아먹는다. 예: 평일 35일이라도 주간 전일 녹음 7일 + 편집 2일을 빼면 실제 녹음일은 26일뿐이다. 이 차감을 빠뜨리면 용량을 27% 과대평가한다.

## 3단계: 전역 타당성

```
필요 페이지 = Σ(kind == "paged" 인 도서의 pages)
상한 용량   = 가용 녹음일 × 일일 상한
```

`필요 페이지 > 상한 용량` 이면 **불가능**이다. 초과량과 함께 완화 수단을 비용이 낮은 순으로 제시한다:

1. **기간 연장** — 성대 부하가 늘지 않는다. 항상 첫 번째 후보.
2. **근무일 추가** (토요일 등) — 주간 회복일을 잃는다.
3. **일일 상한 초과** — 성대 위험을 직접 늘린다. 마지막 후보이며, 며칠·몇 페이지인지 명시한다.
4. **범위 축소** — 도서 제외/분할. 사용자만 결정할 수 있다.

## 4단계: 구간별 타당성 (놓치기 쉬움)

전역이 통과해도 실패할 수 있다. 마감이 이른 도서가 초반 용량을 잠식하기 때문이다.

각 마감 시점 D에 대해:

```
D 이전 가용 녹음일 × 일일 상한  ≥  D 이전 마감 도서들의 페이지 합
```

예: 전체는 여유로워도 "150p를 2주 안에" 는 평일 10일 − 전일점유 3일 = 7일 → 21.4p/일이 필수 하한이 되어, 같은 기간 다른 도서의 여유를 18p/일로 압축한다. 이 압축이 다른 마감을 깨는지 확인한다.

## 산출 스키마

`_workspace/01_constraint-analyst_constraints.json` 으로 떨어뜨린다. 검증 단계가 이 파일을 정답지로 쓰므로, **모든 제약은 숫자나 날짜로 표현**한다. 산문은 `notes` / `horizon_note` 에만 둔다.

```json
{
  "meta": { "start": "...", "end": "...", "working_days": ["MON","..."],
            "daily_page_cap": 40, "daily_page_target": 37,
            "min_books_per_recording_day": 2, "horizon_note": "해석 근거" },
  "books": [ { "id": "kebab-case", "name": "표시명",
               "kind": "paged | full_day_weekly",
               "pages": 600, "deadline": "YYYY-MM-DD", "deadline_rule": "원문",
               "edit_full_days": 1, "continuous": true, "notes": "" } ],
  "capacity": { "weekdays": 0, "youtube_full_days": 0, "edit_full_days": 0,
                "recording_days": 0, "required_pages": 0,
                "cap_capacity_pages": 0, "avg_per_recording_day": 0.0,
                "slack_pages": 0 }
}
```

필드 의미:

- `kind: "paged"` — 페이지 예산을 소비하는 도서.
- `kind: "full_day_weekly"` — 페이지 산정 대상이 아니고, 주 1일을 통째로 점유한다 (`pages: null`).
- `continuous: true` — 전 기간 매 녹음일에 반드시 배치되어야 하는 상주 도서.
- `daily_page_target` — 상한보다 낮게 둔다. 이유는 `vocal-load-scheduling` 스킬 참조.

## 보고 형식

타당성 결과는 표로 보고한다. 해석별로 한 행씩:

```
6주 (10/2):  평일 30 | 녹음가능 22일 | 필요 950p | 일평균 43.2p | 상한용량 880p | 초과 70p
7주 (10/9):  평일 35 | 녹음가능 26일 | 필요 950p | 일평균 36.5p | 상한용량 1040p | 가능
```

"가능/불가능"만 말하지 않고 일평균을 함께 보인다. 상한 이내라도 일평균이 상한에 붙어 있으면 컨디션 변동을 흡수할 여유가 없다는 신호다.
