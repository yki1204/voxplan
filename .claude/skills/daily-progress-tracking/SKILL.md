# 일별 실적 추적

계획은 고정하고, **실제 실적과 계획의 차이를 주말 보충 분량으로 흡수**한다. 미달이 생겼다고 평일 배분을 다시 짜지 않는다.

## 왜 재배분하지 않는가

하루 미달마다 전체 일정을 다시 계산하면 세 가지가 깨진다.

1. **습관이 깨진다.** 매주 월요일이 전일 녹음이라는 리듬이 흔들리면 계획을 신뢰할 수 없게 된다.
2. **마감 구조가 흔들린다.** 한 도서의 미달을 뒤로 밀면 다른 도서의 마감 구간을 침범한다.
3. **성대 부하 평준화가 무너진다.** 미달분을 남은 평일에 얹으면 일부하가 상한에 붙는다.

그래서 미달분은 평일 계획을 건드리지 않고 **그 주 주말로 격리**한다. 주말은 원래 계획에서 비어 있으므로 완충으로 쓸 수 있고, 한 주 안에서 정산되므로 부채가 무한히 누적되지 않는다.

## 이월 계산 규칙

도서 `b`, 주 `w` 에 대해 순서대로 계산한다. **주 단위로 정산하고, 일 단위로 정산하지 않는다** — 화요일에 초과 녹음하면 수요일 목표가 자연히 줄어야 하는데, 일 단위 정산은 그것을 표현하지 못한다.

```
P(b,w)        = w 주 "정산 대상" 평일의 계획 페이지 합
carry_in(b,w) = carry_out(b, w-1)          (첫 주는 0)
due(b,w)      = P(b,w) + carry_in(b,w)     이번 주가 실제로 갚아야 할 양

주말배정(b,w) = max(0, due − 평일실적합)   ← 주말이 맡게 된 양
주말잔여(b,w) = max(0, 주말배정 − 주말실적합)  ← 그중 아직 못 한 양
carry_out(b,w)= max(0, due − 평일실적합 − 주말실적합)
선행(b,w)     = max(0, 평일+주말실적합 − due)
```

**정산 대상 판정이 이 계산의 핵심이다.** 어떤 날을 정산할지 틀리면 나머지가 모두 어긋난다.

- 정산 대상 = **지난 날** 또는 **실적이 입력된 날**
- 날짜만으로 판정하면 일정 시작 전에 미리 입력해도 미달이 잡히지 않아, 주말 칸이 영원히
  '예정'에 머문다. 사용자에게는 기능이 고장 난 것으로 보인다.
- 반대로 아직 오지 않았고 실적도 없는 날은 미달이 아니다. 월요일에 그 주 전체가 미달로
  집계되면 매주 초 '재계획 필요'가 뜬다.
- 주 단위 phase 도 같은 규칙을 따른다: 금요일이 지났으면 `past`, 시작했거나 실적이 있으면
  `current`, 그 외 `future`.

**"배정"과 "잔여"를 구분해 표시한다.** 주말에 7p가 배정됐고 7p를 채웠다면 잔여는 0이다.
배정량만 보여주면 다 해도 숫자가 줄지 않아 입력이 반영되지 않는 것처럼 보인다.
용량 경고도 잔여가 0이면 내린다 — 이미 해결된 경고를 계속 띄우면 신호가 무의미해진다.

핵심 두 가지:

- **주말 실적까지 반영한 뒤에도 남으면 다음 주로 이월된다.** 주말에 보충하지 않은 분량을 0으로 처리하면 숫자가 거짓이 된다. 이월은 빨간 상태로 드러내야 한다.
- **선행분은 다음 주 계획을 줄이지 않는다.** 줄이면 그것이 곧 재배분이다. 선행은 전체 진행률에만 반영하고, 평일 계획은 그대로 둔다.

## 주말 용량 가드레일

주말 보충도 성대 부하 상한을 받는다. 주말 2일 × 일일 상한이 물리적 한계다.

| 주말잔여 총량 | 판정 | 표시 |
|---|---|---|
| 0 | 정상 | 잔여 없음 |
| ~ 일일 상한 | 하루로 소화 가능 | 보통 |
| 일일 상한 ~ 2일분 | 주말 이틀 필요 | 주의 |
| 2일분 초과 | **주말로 흡수 불가** | 경고 — 재계획 검토 |

마지막 구간에 들어가면 이월 규칙으로 감출 수 없다. 그때는 사용자에게 재계획(기간 연장 / 범위 축소)을 제안한다. 이 가드레일이 없으면 이월이 조용히 쌓여 마감 직전에 터진다.

## 진행률

두 숫자를 **함께** 보여준다. 하나만으로는 상태를 알 수 없다.

- **절대 진행률** = 누적 실적 / 전체 페이지 — 얼마나 왔는가
- **계획 대비 편차** = 오늘까지 누적 실적 − 오늘까지 누적 계획 — 앞서 있는가 뒤처져 있는가

절대 진행률만 보이면 "60% 했으니 괜찮다"는 착시가 생긴다. 계획상 75%여야 하는 시점이면 뒤처진 것이다.

페이지가 없는 항목(전일 녹음, 편집일)은 페이지 진행률에서 제외하고 **완료 여부 토글**로만 추적한다. 페이지 예산을 소비하지 않으므로 진행률 분모에 넣으면 왜곡된다.

## 저장

브라우저 `localStorage` 단독으로 저장한다. 서버가 없으므로 정적 호스팅(GitHub Pages 등)에
그대로 올려도 동작하고, 런타임 역량·토큰·백엔드가 필요 없다.

- **디바운스를 두지 않는다.** `localStorage` 쓰기는 동기이고 값싸다. 입력 즉시 기록하면
  "아직 저장 안 된 몇 초"가 존재하지 않으므로 사용자가 잃을 구간이 없다. 디바운스는
  네트워크 저장(버전을 만드는 발행 등)에서만 필요하다.
- **저장 실패를 조용히 넘기지 않는다.** 시크릿 창이나 사이트 데이터 차단 환경에서는
  `setItem` 이 던진다. 로드 전에 probe(`setItem`+`removeItem`)로 가용성을 확인하고,
  막혀 있으면 화면에 **저장 불가**로 표시한다. 공유되는 줄 알고 쓰다가 잃는 것이 최악이다.
- **화면은 저장이 막혀도 동작해야 한다.** 저장 불가가 렌더 실패로 번지면 계획표조차 못 본다.
- **저장 범위를 사용자에게 명시한다.** 유지되는 경우(새로 고침·탭 닫기·브라우저 재시작·재배포)와
  유지되지 않는 경우(다른 기기·다른 브라우저·시크릿 창 종료·사이트 데이터 삭제)를 문구로 구분한다.
- **키는 프로젝트 단위로 이름공간을 준다.** 정적 호스팅에서는 `user.github.io/a/` 와
  `user.github.io/b/` 가 같은 origin 을 공유하므로, 키가 겹치면 다른 프로젝트의 데이터를 덮는다.

기기 간 공유나 대화에서 읽기가 필요해지면 그때 저장 계층만 바꾼다. 파생값을 저장하지 않는
설계(아래) 덕분에 계산 로직은 그대로 재사용된다.

## 숨겨둔 보상 (선택)

마일스톤에 보상을 걸어 둘 때의 규칙:

- **발견 전에는 HTML 본문에 노출하지 않는다.** 정의를 스크립트 안에만 두어 소스를 대충
  훑어도 눈에 걸리지 않게 한다. 숨긴 것이 마크업에 그대로 있으면 숨긴 것이 아니다.
- **판정은 입력이 멈춘 뒤에 한다.** 타이핑 중에 모달이 포커스를 훔치면 남은 키 입력이
  유실된다. 마지막 입력 후 1초 가까이 디바운스한다.
- **한 번 뜨고 사라지게 두지 않는다.** 캡처해서 공유해야 하는 보상이면 나중에 다시 열 수
  있어야 한다. 획득 목록을 남기고 눌러서 재열기를 제공한다.
- **여러 개가 동시에 열리면 큐로 순차 표시한다.** 겹쳐 띄우면 뒤의 것을 못 본다.
- **획득 시각을 상태에 저장한다.** 재실행 시 다시 뜨지 않게 하고, 보상 번호를
  획득 시각으로 재현 가능하게 만든다.

## 데이터 스키마

```json
{
  "v": 1,
  "ts": 1756000000000,
  "actuals": { "2026-08-25": { "major-book": 22, "lebanon": 14 } },
  "done":    { "2026-08-24": true },
  "found":   { "coffee": 1756000000000 }
}
```

- `actuals` — 날짜별·도서별 실제 녹음 페이지. 주말 보충은 **토요일 날짜**에 기록해 주말 단위로 다룬다.
- `ts` — 마지막 저장 시각. 상태칩의 저장 시간 표시에 쓰고, 저장 계층을 바꿀 때 신·구 판별에 쓴다.
- `done` — 페이지가 없는 전일 항목(전일 녹음·편집)의 완료 여부.
- `found` — 마일스톤 보상의 획득 시각. 재방문 시 중복 팝업을 막고 보상 번호를 재현한다.
- 계획값은 여기에 넣지 않는다. 계획의 단일 출처는 `_workspace/02_optimizer_schedule.json` 이고, 실적만 이 파일에 쌓인다. 둘을 한 파일에 섞으면 재배분 시 실적이 함께 덮인다.

## 파생값은 저장하지 않는다

주말잔여, 이월, 진행률, 편차는 전부 `actuals` + 계획에서 계산된다. 저장하면 계획이 바뀔 때 옛 파생값이 남아 어긋난다. 로드 시와 입력 시 같은 함수로 다시 계산한다.
