# 녹음 일정 오케스트레이터

**실행 모드: 하이브리드**
- Phase 2 (제약 분석): 서브 에이전트 — 단일 산출물, 팀 통신 불필요
- Phase 3~4 (배분 + 검증): 에이전트 팀 — 배분과 검증이 FAIL 루프를 돌며 상호 참조
- Phase 5 (UI 발행): 서브 에이전트 — 확정 데이터를 단방향 소비
- Phase 6 (실적 분석): 서브 에이전트 — 기록된 실적을 읽어 판정, 필요 시 Phase 3으로 회귀

호출 시 모든 `Agent` 호출에 `model: "opus"` 를 명시한다.

## Phase 1: 컨텍스트 확인 (필수, 항상 먼저)

`_workspace/` 상태로 실행 모드를 판별한다.

| 상태 | 모드 | 행동 |
|------|------|------|
| `_workspace/` 없음 | **초기 실행** | Phase 2부터 전체 실행 |
| 있음 + 사용자가 특정 구간/항목 수정 요청 | **부분 재실행** | 해당 에이전트만 재호출, 이후 Phase는 검증→UI만 |
| 있음 + 사용자가 새 입력 제공 (도서 교체, 기간 전면 변경) | **새 실행** | 기존 `_workspace/` → `_workspace_prev/` 로 이동 후 전체 실행 |

**세션이 바뀌어도 상태는 파일에 남아 있다.** `_workspace/` 의 제약·배분·검증 리포트와
CLAUDE.md 변경 이력이 이전 세션의 결론이다. 대화 기록을 복원하려 하지 말고 이 파일들을 읽어라.
단, **발행된 아티팩트를 갱신할 때는 URL이 필요하다** — 이 대화에서 발행하지 않았다면
`Artifact` 도구의 `action: "list"` 로 URL을 찾아 `url` 파라미터로 넘긴다. 빠뜨리면 같은
아티팩트를 갱신하는 대신 별개 아티팩트가 새로 생기고, 사용자가 공유한 기존 링크가 죽는다.

부분 재실행에서도 **검증(Phase 4)과 UI 재발행(Phase 5)은 반드시 다시 거친다.** 배분을 한 군데 고치면 총량 제약이 깨지는 일이 흔하고, JSON만 고치고 UI를 놔두면 화면과 데이터가 갈라진다.

## Phase 2: 제약 분석 — `constraint-analyst`

**스킬:** `recording-constraint-modeling`
**출력:** `_workspace/01_constraint-analyst_constraints.json`

- 기간 표현이 중의적이면(예: "한달 반") 해석별로 타당성을 모두 계산해 표로 제시한다.
- 전역 타당성 + 마감별 구간 타당성을 모두 검사한다.
- **불가능 판정이면 여기서 멈추고 사용자에게 완화안을 제시한다.** 배분을 강행하지 않는다.
- 일평균이 밴드 하한에 미달하면 그것도 보고한다 — 기간이 불필요하게 길다는 신호다.

## Phase 3: 배분 — `schedule-optimizer`

**스킬:** `vocal-load-scheduling`
**출력:** `_workspace/02_optimizer_schedule.json`

- 마감 순 확정 → 상주 도서로 잔여 충전.
- 일일 목표는 상한보다 5~10% 낮게.
- 배분은 코드로 생성하고 총량 assert 통과.

## Phase 4: 검증 — `schedule-validator`

**스킬:** `schedule-validation`
**출력:** `_workspace/03_validator_report.md`

- 번들 스크립트를 **실제 실행**하고 원본 출력을 리포트에 붙인다.
- FAIL이면 위반 항목과 수치를 `schedule-optimizer` 에 넘겨 Phase 3으로 되돌린다.
- WARN은 원인 규명 후 불가피/재배분 중 하나로 결론 낸다.
- Phase 3↔4 루프는 **최대 2회**. 2회 후에도 FAIL이 남으면 남은 위반을 명시해 사용자에게 올린다.

## Phase 5: UI 발행 — `schedule-ui-builder`

**스킬:** `schedule-ui-rendering` (+ `artifact-design` 선행 로드)
**출력:** `index.html` + Artifact URL

- 착수 조건: Phase 4 FAIL 0.
- 재발행은 같은 파일 경로로. 이전 세션 아티팩트 갱신 시 `action: "list"` 로 URL 확보 후 `url` 전달.

## Phase 6: 실적 분석 — `progress-analyst`

**스킬:** `daily-progress-tracking`
**출력:** `_workspace/04_progress-analyst_status.md`

실적은 브라우저 `localStorage`(키 `voxplan.checkins.v1`)에만 있어 **읽을 수 없다.**
사용자에게 화면 캡처나 콘솔 값(`localStorage.getItem("voxplan.checkins.v1")`)을 요청해
계획과 대조한다. 받지 못했으면 추정하지 말고 "실적 미확인"으로 보고한다.

- **절대 진행률과 계획 대비 편차를 항상 함께** 낸다. 하나만으로는 상태를 알 수 없다.
- 미달은 기본적으로 **주말 이월 규칙으로 흡수**한다. 하루 미달마다 재배분을 제안하지 않는다 —
  평일 계획 고정이 이 시스템의 설계 의도다.
- **주말잔여가 주말 용량(2일 × 일일 상한)을 넘거나 2주 연속 이월**이면 `재계획 필요` 로 판정하고
  Phase 3으로 회귀한다. 이 선이 흡수 가능과 재계획을 가르는 기준이다.
- 파생값(진행률·이월)은 저장된 값을 읽지 않고 계획 + 실적에서 다시 계산한다.

## Phase 7: 피드백 수집

결과 보고 후 개선 여지를 묻는다. 피드백 라우팅:

| 피드백 | 대상 |
|--------|------|
| 페이지 수/날짜/도서 조합 | Phase 3 재배분 → 4 → 5 |
| 마감/상한/근무일 조건 | Phase 2부터 |
| 색·배치·라벨·강조 | Phase 5만 |
| 이월 규칙·진행률 계산 | `daily-progress-tracking` 스킬 수정 후 Phase 5 |
| 실적이 계획을 못 따라감 | Phase 6 판정 → 필요 시 Phase 3 |
| 배분 근거가 납득 안 됨 | `vocal-load-scheduling` 스킬 자체 수정 |

## 데이터 전달 프로토콜

- **파일 기반** (`_workspace/{phase}_{agent}_{artifact}.{ext}`) — 산출물 본체. 중간 파일은 삭제하지 않고 보존한다(사후 검증·감사 추적).
- **태스크 기반** (`TaskCreate`/`TaskUpdate`) — Phase 3↔4 루프의 FAIL 항목 추적.
- **메시지 기반** (`SendMessage`) — 검증가→최적화가 위반 통보.

## 에러 핸들링

| 상황 | 대응 |
|------|------|
| 타당성 불가 | Phase 2에서 중단, 완화안(기간 연장 → 근무일 추가 → 상한 초과 → 범위 축소) 제시 |
| 검증 스크립트 예외 | 데이터 문제/스크립트 버그를 먼저 구분. 버그면 고치고 고친 사실을 보고 |
| Phase 3↔4 루프 2회 초과 | 남은 FAIL을 명시해 사용자에게 올림. 검증 기준 완화는 금지 |
| 제약 파일 자체 모순 | Phase 2로 되돌림 |
| Artifact 발행 실패 | 로컬 `index.html` 경로와 실패 원인 함께 보고 |
| 에이전트 1회 실패 | 1회 재시도. 재실패 시 해당 결과 없이 진행하고 보고서에 누락 명시 |

## 테스트 시나리오

**정상 흐름:** 도서 3권(150p/2주, 200p/1달, 470p/2달) + 주간 전일 녹음 1권, 상한 30~40p, 월~금.
→ Phase 2에서 종료일 후보별 일평균 비교 → 밴드 내 최적안 선택 → 22 녹음일 배분 → 검증 FAIL 0 → UI 발행.
기대: 모든 일부하 30~40p, 모든 마감 충족, 상주 도서 전 녹음일 배치, 단일 도서 구간은 이유 명기 + 세션 분할.

**에러 흐름:** 같은 조건에서 종료일을 6주로 고정하고 총량을 950p로 올린다.
→ Phase 2가 `초과 70p` 로 불가 판정 → 배분 진입하지 않고 완화안 4종 제시 → 사용자 선택 대기.
기대: 실행 가능하지 않은 일정표를 만들지 않고 중단한다.

**실적 흐름:** 일정 발행 후 "화요일에 자율 전공책 15p만 했어".
→ Phase 6이 그 주 주말잔여 7p로 계산 → 주말 용량 이내이므로 `흡수 가능` 판정 →
평일 계획을 건드리지 않고 주말 칸에만 반영.
기대: 재배분을 제안하지 않는다. 반대로 2주 연속 이월이나 주말 용량 초과가 되면
`재계획 필요` 로 판정해 Phase 3으로 되돌린다.

**후속 흐름:** 기존 산출물 존재 상태에서 "레바논 470p, 2달로 변경".
→ Phase 1이 부분 재실행 판정 → Phase 2에서 해당 도서만 수정 후 타당성 재계산 → Phase 3 재배분 → Phase 4 전체 재검증 → Phase 5 같은 URL 재발행.
기대: 기존 `_workspace/` 를 덮되 이전 결과와의 차이(총량, 종료일, 일평균)를 함께 보고한다.
