# 스케줄 검증

스케줄 파일과 제약 파일을 **동시에 읽고 항목별로 대조**한다. 스케줄 하나만 보고 "잘 짜인 것 같다"고 판정하는 것은 검증이 아니다.

## 스크립트를 실행한다

```bash
python3 .claude/skills/schedule-validation/scripts/validate_schedule.py \
  _workspace/01_constraint-analyst_constraints.json \
  _workspace/02_optimizer_schedule.json
```

종료코드 0 = 전부 통과, 1 = FAIL 존재, 2 = 인자 오류.

**출력을 눈으로 확인한 뒤에만 통과를 주장한다.** 수십 일 × 여러 도서의 산술은 육안 검증이 불가능하다. 검증 결과를 보고할 때는 실행한 명령과 원본 출력을 함께 붙인다.

## 스크립트가 검사하는 것

| 항목 | 판정 |
|------|------|
| 근무일 외 배치 | FAIL |
| 일일 페이지 > 상한 | FAIL |
| `total_pages` 와 블록 합 불일치 | FAIL |
| 도서별 녹음 총량 ≠ 선언 페이지 수 | FAIL |
| 편집 전일 수 ≠ 요구 수 | FAIL |
| 녹음 종료일 또는 편집일 > 마감 | FAIL |
| `continuous` 도서가 빠진 녹음일 | FAIL |
| 주간 전일 녹음이 없는 주 | FAIL |
| 미정의 도서 id | FAIL |
| 녹음일 수 ≠ 제약 선언값 | FAIL |
| 녹음일에 단일 도서만 배치 | WARN |
| 한 주에 전일 녹음 2회 이상 | WARN |

## 스크립트가 못 잡는 것

자동 검증은 하드 제약만 본다. 아래는 두 파일을 읽고 사람이 판단한다:

- **전일 점유일의 요일 선택**이 성대 회복 논리에 맞는가 (주간 전일 녹음이 주 초반인가)
- **편집일이 녹음 부하가 몰린 구간 직후**에 놓였는가
- **일부하가 평탄한가** — 주별 평균의 분산을 확인한다. 특정 주에 몰려 있으면 상한을 지켰어도 위험하다
- **일평균이 밴드 하한에 미달**하지 않는가 — 미달이면 기간이 불필요하게 길고 단조 구간이 늘어난 것이다
- **단일 도서 구간에 세션 분할 완화**가 적용되었는가

## WARN 처리 원칙

WARN은 무시 대상이 아니다. 각 WARN에 대해 원인을 규명하고 다음 중 하나로 결론 낸다:

- **구조적으로 불가피** — 근거를 명시한다. 예: "해당 날짜 이후 다른 도서가 모두 마감 → 혼합 불가". 이 경우 완화(세션 분할)가 적용됐는지 확인한다.
- **배분으로 해소 가능** — `vocal-load-scheduling` 으로 되돌려 재배분한다.

**검증 기준을 느슨하게 바꿔 통과시키는 것은 금지한다.** FAIL이 났다면 배분을 고친다. 스크립트에 실제 버그가 있어 고친 경우에는 무엇을 왜 고쳤는지 보고한다.

## 재검증

수정 후에는 수정 구간만이 아니라 **전체를 다시 돌린다**. 한 주의 배분을 바꾸면 총량 제약이 깨지는 일이 흔하다. 그리고 지난 리포트의 FAIL/WARN이 실제로 해소되었는지부터 확인한다 — 미해소 항목이 조용히 사라지는 것을 막는 것이 재검증의 핵심이다.
